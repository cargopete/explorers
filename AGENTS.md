# explorers — AGENTS.md

## Scope

Unified block explorer provider library. Normalizes balances, tx history, contract info, token holdings, gas data, and block info across multiple chains and explorer APIs. Exports both CLI (`explorers` binary) and programmatic API.

## Conventions

- Chain names normalized via `normalizeChain()`, which takes display names as well as aliases like `ethereum`, `mainnet`, `arb`, `btc`
- Native and token amounts use strings in each chain's smallest unit — call `formatWei(value, decimals)` with the asset's decimals; its default is 18
- `noUncheckedIndexedAccess` and `noImplicitOverride` are enabled — guard indexed access and mark overrides explicitly
- Provider registration runs off a manifest: `src/providers/index.ts` lists every built-in as `{ key, chains, capabilities, chainGaps?, defaultURL?, load }`, where `chainGaps` names the declared capabilities a provider still refuses on one chain, so routing and refusal hints skip it there, and `core/registry.ts` turns that list into its map on the first registry call. The class itself only owns `static readonly key`
- Provider backends are explorer/indexer APIs, including documented gateway APIs. Judge support by the service and response contract, not REST versus GraphQL: a gateway may expose REST routes shared with nodes. Do not silently switch to another node to fill a missing capability. Unsupported operations stay absent; required methods without a supported service contract throw `UnsupportedOperationError`.
- `Transaction.to` is `null` whenever the explorer names no recipient, not only on a contract creation: Solscan, Helius and Blockberry never name one, and an Arweave data upload keeps the documented `""`. Etherscan and Blockscout put the deployed address in `createdContract`, and the CLI, Pi and OMP renderers print a sender, a recipient or a created contract only when the record has one, a `?` in place of a missing sender or recipient in a history line. `Transaction.from` stays a string and is `""` when the explorer names no sender, as on Blockchair UTXO dashboards
- Transactions in the Bitcoin family carry their OP_RETURN pushes in `Transaction.opReturn`, read by `collectOpReturns()` in `core/script.ts` from the output scripts `mempool`, `blockstream`, `blockchair`, `whatsonchain`, `blockbook` and `haskoin` hand out, Bitcoin SV's `OP_FALSE OP_RETURN` included; each payload keeps its raw `hex` and gets a `text` reading only when the bytes are printable UTF-8
- Transaction detail from `mempool` and `blockstream` carries Ordinals inscriptions in `Transaction.inscriptions`: `collectInscriptions()` reads the `OP_FALSE OP_IF "ord" … OP_ENDIF` envelopes of each input's tapscript the way ord does (the opening matched by pushed value, not by push encoding, then field pairs up to the first empty push, then body chunks) and gives `input`, `contentType`, `contentEncoding` and `size`, plus `hex` and a printable `text` only for a body of 1 to 4096 bytes. History rows leave inscriptions out
- `mempool` and `blockstream` answer `getPubkey` from the Esplora address feed in `core/esplora.ts`: the counters of `/api/address/:address` first, so an address without transactions costs one request and one that never spent stops after the first page, then the feed newest first until an input spending from the address carries a key (last scriptSig push for P2PKH, `witness[1]` for P2WPKH and P2SH-wrapped P2WPKH) or a taproot output names it, at most `ESPLORA_HISTORY_ROWS` rows, `PEPPOOL_KEY_ROWS` (250) on Pepecoin, where Peppool allows 15 requests a minute and answers 429 with a `Retry-After` near a minute. Consensus already ties such a key to the address, so nothing hashes it again. `pubkey: null` with `spent: true` means a script the reader leaves alone or a spend past that window
- `mempool` and `blockstream` look for an address in feed rows through `esploraFeedAddress()`, never the raw input: BIP 173 lets a QR code carry segwit in capitals, the feed writes it in lowercase, and a raw match turns a spend into a receive of 0. Results keep the caller's spelling
- `mempool` and `blockstream` list unspent outputs through Esplora `/api/address/:address/utxo`, `whatsonchain` through `/address/:address/unspent/all`, `blockbook` through `/api/v2/utxo/:address`, `haskoin` through `/address/:address/unspent`. A `Utxo` row keeps `txid`, `vout`, `value` as a base-unit string and the funding block, `null` while the output waits in the mempool. Providers without such an endpoint keep `utxos: false` and no `getUtxos` method
- CLI default command: `providers` for an empty line; a first word that names no command, such as an address, runs `balance`
- Error hierarchy: `ExplorerError` → `HTTPError`, `TransportError`, `AuthError`, `RateLimitError`, `BlockedError`, `PlanRestrictedError`, `NotFoundError`, `UnsupportedChainError`, `UnsupportedOperationError`, `UnknownProviderError`, `AddressChainMismatchError`
- `withProvider()` ends an `UnsupportedChainError` or `UnsupportedOperationError` from the provider it ran with `; try <providers>` (those the registry says serve that chain and read) or `; no provider serves this read on <chain>`; a chain refusal from a read without a capability names only who serves the chain (`; solscan, helius serve solana`), and `UnknownProviderError` lists the registered names, because MCP, Pi, OMP and the CLI show only the message. A thrown operation outside `OPERATION_CAPABILITIES` in `core/provider.ts` keeps its bare message
- HTTP client runs on native `fetch` with a 15s default timeout and reads every body as text, so out-of-range JSON integers survive as strings. The timeout is a plain timer cleared once the body is in, which fake timers can move, and a caller's signal joins it through `AbortSignal.any`. A 400 to 599 answer becomes a `ResponseFailure` carrying the fields of ofetch's `FetchError`, so `normalizeError` reads it and a custom provider's own ofetch error the same way. A request that dies before its whole body arrives leaves as `NoResponse`, which `normalizeError` turns into `TransportError` whatever the runtime called the cause (`fetch failed` on Node, `Network connection lost` on Workers)

## Key files

- `src/core/types.ts` - re-exports `ChainKey` from `@agntn/chains`; owns transaction, balance, token, contract, gas, block, and provider-config types
- `src/core/provider.ts` - abstract `Provider` base class and optional operation contract. `getJSON`/`postJSON` retry HTTP 429 and JSON that mentions a rate limit on the same backend with backoff
- `src/core/errors.ts` - ExplorerError hierarchy + normalizeError. HTTP 429 copies `Retry-After` onto `RateLimitError.retryAfter`. A response carrying `cf-mitigated: challenge` becomes `BlockedError` whatever its status, so a Cloudflare bot check never reads as a missing key and `Provider` never retries it. A request with no response becomes `TransportError` with the reason and code of its innermost cause, never an `HTTPError` with status 0. An `HTTPError` message ends with the reason from the response body (plain text, or the first `reason`, `detail`, `message`, `error` or `title` field of JSON, at the top or one level down), one line of at most 200 characters without control bytes, because every surface shows only the message; `HTTPError.reason` holds that reason alone
- `src/core/registry.ts` - Provider registry built from `builtins` on first use; `create()` is async and imports one provider (register, create, providers, listProviders, has). `listProviders()` describes every provider from metadata and backs the `providers` command and `explorers_providers` on MCP, Pi and OMP
- `src/core/resolve.ts` - Auto-select built-in providers by env vars and chain, with one fallback after no answer, a 5xx, or a rate or plan limit that survived retries on that backend
- `src/core/client.ts` - HTTP client wrapper over native `fetch`
- `src/core/ens.ts` — ENS resolution (public APIs, no keccak dependency)
- `src/core/input.ts` — User input classification (address/txhash/ens)
- `src/providers/*.ts` — One file per provider, each exporting its class, listed in `builtins` and built as its own bundle entry
- `src/tools.ts` - one `defineTool` per tool from `@agntn/tools`: the eleven `explorersTools()` that MCP, Pi, OMP and the CLI share, the two `explorersCommands()` only the CLI gets (`balance` with address words, `tx` that tells a hash from an address), `describeCall()` for host call lines. Schemas use `Type` from `@agntn/tools`, never a bare `typebox`, and constants come from `tool-limits.ts`, which imports nothing
- `src/tool-operations.ts` - the executors, loaded on the first call. Every answer is compact JSON of the `details` record, with C1, bidi marks and U+2028/9 escaped by `compactJson()`
- `src/tool-lines.ts` - `describeResult()` and `terminalLines()`, the lines Pi and OMP draw from `details`, each through `sanitizeLine`
- `src/mcp.ts` - `createMcpServer()`, which `explorers mcp` puts on stdio and `@agntn/explorers/mcp` exports for a host with its own transport. It is its own input in `build.config.ts`, so it shares chunks and the registry with `dist/index.mjs`
- `src/cli.ts` - CLI entry point; `src/cli-run.ts` hands the tools to `runCli` from `@agntn/tools/cli`. Inside a checkout, the built `dist/cli.mjs` loads the `mcp` command from `src/`, like the Pi and OMP extensions, so a local MCP server needs only a restart after a change. The npm package ships no `src/` and runs the bundle, and so does a copy under `node_modules`, where Node does not strip types. `EXPLORERS_DIST=1` forces the bundle. A closed stdout or stderr (`| head -1`) ends the process through the `EPIPE` listener of `runCli` and keeps the exit code. A change to `src/cli.ts` itself still needs `pnpm build`

## CLI subcommands

`balance`, `tx`, `tx-history`, `tx-detail`, `utxos`, `pubkey`, `contract`, `tokens`, `transfers`, `gas`, `block`, `providers`, `mcp`, one per tool from its schema - all support `-c` (chain), `-p` (provider). Each prints the tool's compact JSON, `--json` its details. `tx` accepts `-m history|detail` to resolve ambiguous hash/address formats. `transfers` accepts `-t` to limit results to one token contract. `tokens` lists fifty holdings unless `-n` says otherwise, a hundred at most, with `total` counting every one. `utxos` cuts its outputs the same way, with `total`, `confirmed` and `pending` over every output. `tx`, `balance`, `tokens` and `transfers` support ENS.

## Constraints

- Etherscan: 5 req/s free tier, needs `ETHERSCAN_API_KEY`
- Blockscout serves the complete holding array from `/addresses/:address/token-balances`; large wallets can produce multi-megabyte responses, so this read allows 60 seconds unless `ProviderConfig.timeout` overrides it.
- Blockchair: data format differs between UTXO (bitcoin, bitcoincash, litecoin, dogecoin, ecash, zcash) and EVM chains; eCash amounts are satoshis at 2 decimals (100 satoshis = 1 XEC). Bitcoin Cash lives under the `bitcoin-cash` slug, and its address dashboard takes CashAddr with or without the `bitcoincash:` prefix as well as the legacy form. Zcash amounts are zatoshis (8 decimals) of the transparent side only: a fully shielded transaction reads as value and fee `"0"`
- Blockchair answers a spent limit with 402 or 435 to 437 and a blocked IP with 430 or 434. `read()` in the provider turns those into `RateLimitError` with `context.error` in the message, outside `Provider` retries, since a block does not clear in seconds; a keyless block also names `BLOCKCHAIR_API_KEY`. A rejected key shares 402, and only `context.error` ("Invalid API token") tells it apart, so `read()` throws `AuthError` for it and an automatic read does not fall back
- Solscan, Helius, TONAPI, TRONSCAN, Aptos, Blockberry, Horizon, WhatsOnChain, Blockbook, Haskoin, eCash Explorer and XRPSCAN are single-chain providers and throw `UnsupportedChainError` for other chains.
- Helius Enhanced Transactions v0 exposes no REST balance endpoint, so `getBalance` throws `UnsupportedOperationError`; the key travels as the `api-key` query parameter, which `sanitizeUrl` redacts.
- Helius `getTokenBalances` calls DAS `searchAssets` on the RPC root, so it answers over JSON-RPC and a failure arrives as `error` inside a 200 response. Pages hold 1000 assets and the walk stops after 20 of them.
- Arweave has three gateway providers on one class: `arweave` (arweave.net) in `providers/arweave.ts`, and `turbo` (turbo-gateway.com) and `ario` (ar-io.dev) as subclasses that only swap the default gateway. No gateway indexes everything: arweave.net and permagate.io lack 2019 layer 1 transfers and turbo-gateway.com lacks some data items near block 1,700,000 that ar-io.dev keeps. Automatic selection ranks `turbo`, `ario`, `arweave` through their order in `ENV_MAP`, so a 5xx from Turbo moves the read to ar-io.dev. Each gateway uses REST for `/wallet/{address}/balance` and `/block/height/{height}`, and GraphQL for transactions. It merges owner and recipient queries, removes self-transfer duplicates, and caps the history window at `page * limit <= 1000` with `limit` from 1 to 100. `baseUrl` is the gateway root for both APIs. Balance snapshot height/hash stay null because the endpoint does not return them. Block gas fields use `"0"` as the existing non-EVM convention; storage price quotes are not gas data. Contracts and token operations stay unsupported. Amounts use winstons (12 decimals), missing recipients stay empty strings, and bundle fees are not attributed to individual data items. arweave.net answers `bundledIn { id: "" }` on every row and may leave `data.size` null, so a data item shows only by its zero fee, which no layer 1 transaction pays. Block bounds go out as the `BlockFilter` that `transactions(block:)` takes. `TxHistoryOptions.tags` goes out as the `[TagFilter!]` list `transactions(tags:)` takes: a tag matches any of its values, every tag must match, and `[]` is no filter. An empty name or value list throws, because the gateway answers it with no rows. Arweave alone declares the optional `txHistoryTags` capability, and `explorers_tx_history` selects by it when `tags` is not empty and refuses `tags` on a provider without it. Arweave transaction IDs and addresses share their shape, so CLI detail reads require `-m detail`.
- Aptos Explorer has no documented account/history API; `aptos` remains registered with false capabilities and throws `UnsupportedOperationError` instead of using fullnode REST.
- TONAPI and Blockberry do not expose block lookup compatible with the library's single block-number contract, so `blockInfo` is unsupported.
- Mempool: Bitcoin, Litecoin and Pepecoin; Litecoin uses litecoinspace.org, while peppool.space serves balances and transactions but lacks fee recommendations and complete normalized block metadata, so the manifest lists `gasData` and `blockInfo` under `chainGaps.pepecoin`. Peppool paginates confirmed address history with `?after_txid=`, not Esplora's `/txs/chain/:txid` route
- Blockstream serves Bitcoin through the Esplora wire format; its `/api/fee-estimates` response does not match Mempool's recommendation shape, so gas data stays unsupported
- Koios answers on POST with the address or hash in the request body, and the public instance rejects a body over 5120 bytes, so `getTxHistory` asks `tx_info` for 70 hashes at a time and reorders the answer, which comes back in the endpoint's own order
- Koios `address_info` ships the whole UTxO set of an address, 222 kB for a busy one, so `getBalance` narrows the payload with the PostgREST `select` parameter; the endpoint still builds that set before it answers, and a busy address takes 3 to 9 seconds against the 15-second client timeout
- Koios keeps the phase-2 validity flag behind the heavier `_scripts` payload, so a Cardano transaction reads as `success` even when a failing script consumed its collateral; `isContractInteraction` comes from the presence of collateral inputs
- dcrdata uses Insight for Decred balances, transaction history/details and blocks. `baseUrl` is the Insight API root. Amounts use atoms (8 decimals). Balance and funded/spent totals stay confirmed, the signed mempool delta goes to `unconfirmed`, and snapshot fields stay null. The balance is not a spendability check. Chain/address format checks use `@agntn/chains`; checksum validation belongs to the service. History uses `from`/`to` pagination, supports limits 1 to 250 and both sort directions, and rejects unsupported block bounds. Transaction values pair with one addressed output, with full inputs/outputs in `raw`; positive confirmations do not independently prove stake-vote approval. Block responses are arrays and count regular plus stake transactions; miner stays empty and gas fields use "0". Insight's estimatefee is only a relay fee, so gas data remains unsupported.
- Horizon serves Stellar from the SDF's public instance at horizon.stellar.org, keyless, with one year of history; `baseUrl` is any other Horizon root. Amounts are stroops (7 decimals) and Horizon prints them as decimals, so `toStroops` converts without floats. `getBalance` reads `/accounts/{id}` and keeps snapshot fields null; an account the ledger never funded is a 404, so `NotFoundError`. Issued assets are `CODE:ISSUER` (SEP-11) with 7 decimals; trustlines back `getTokenBalances`, liquidity pool shares stay out. History is `/accounts/{id}/payments?join=transactions`, one row per payment-like operation (payment, path payments, create_account, account_merge, invoke_host_function with its balance changes), failed ones included with `status: "failed"` and no token transfers; rows of one transaction share its hash and only a single-operation transaction carries `fee`. `limit` up to 200, `page` up to 10 by walking cursors, no ledger bounds. `getTokenTransfers` scans up to five pages of 200 payments client-side, `token` filters one `CODE:ISSUER`. `getTxDetail` joins `/transactions/{hash}` with its operations: the first payment-like one is the row, every issued-asset movement lands in `tokenTransfers`, Soroban operations set `isContractInteraction`. Gas is `/fee_stats` in stroops per operation: `baseFee` is the ledger base fee, `safeGasPrice` the mode of `fee_charged` (100 outside surge pricing, the marginal inclusion fee inside it), `fastGasPrice` its p95, which Soroban resource fees dominate; no `proposedGasPrice`, because every percentile between mixes classic and Soroban operations. A ledger is a block with `txCount` counting successful and failed transactions, `baseFee` its base fee, miner empty and gas fields `"0"`. Contracts stay unsupported: Soroban state lives behind RPC, not Horizon. Muxed (`M...`) addresses are rejected by `@agntn/chains`
- WhatsOnChain serves Bitcoin SV keyless at 3 requests a second; `WHATSONCHAIN_API_KEY` goes in the `Authorization` header and ranks it like keyed Blockchair. `baseUrl` is the network root. Amounts arrive as BSV JSON numbers, small ones in exponent form, and convert to satoshis from the decimal spelling. Inputs name only the spent output, so sender, fee and the send/receive side come from parent transactions read through `POST /txs`, 20 per request and 200 parents per read; past that `fee` stays absent. History is confirmed only, `limit` up to 100, `page` up to 10 through `next-page` tokens, no block bounds, and each page comes back reversed, one block included, and is reversed again. Unspent outputs drop `isSpentInMempoolTx`, keep `blockHash` null and stop after ten pages. OP_RETURN (bare or `OP_FALSE OP_RETURN`) never becomes the recipient; its pushes go to `opReturn` from `scriptPubKey.hex`. `/feerecommendation` is sat/kB, so gas stays unsupported. Blocks keep `miner` empty and gas fields `"0"`
- Blockbook serves Bitcoin Gold keyless through the public instance at btgexplorer.com; `baseUrl` is the explorer root before `/api/v2`. Amounts arrive as satoshi strings and inputs carry their address and value, so sender and fee need no parent reads. A 400 carries the reason in `error`: "not found" becomes `NotFoundError`, any other reason an `ExplorerError`. History is newest first only (`sort: "asc"` throws), `limit` up to 100, `startBlock`/`endBlock` go out as `from`/`to`, and a page past the end comes back as the last page, so the provider compares the returned `page` and answers `[]`. Mempool transactions read as `pending` at block 0. Unspent outputs keep `blockHash` null. `/api/v2/estimatefee` quotes coins per kB, so gas stays unsupported. OP_RETURN outputs are flagged `isAddress: false` and never become the recipient; their pushes go to `opReturn` from the output `hex`. Blocks keep `miner` empty and gas fields `"0"`
- Haskoin serves Bitcoin Cash keyless through Haskoin Store at api.haskoin.com; `baseUrl` is the network root (`/bch`). Addresses are CashAddr, with or without the `bitcoincash:` prefix, or legacy base58: `@agntn/chains` keeps a bare `1…`/`3…` out of Bitcoin Cash, so the provider checks it as a Bitcoin address and rewrites it to the CashAddr twin over the same hash (type 0 or 1). It compares addresses in the lowercase prefixed spelling Haskoin answers with. Inputs carry address and value, so sender and fee need no parent reads. Balance `confirmed` already drops outputs a mempool transaction spends and `unconfirmed` holds the unspent mempool outputs, so `balance` is `confirmed`, `unconfirmed` is never negative and their sum is the post-mempool total; `funded` is `received` and `spent` the difference. History is newest first only, `limit` up to 100, `page` becomes `offset` (the public instance caps it at 50000), `endBlock` becomes `height` and `startBlock` throws. Deleted transactions read as `failed`, mempool ones as `pending` at block 0. Unspent outputs come in pages of 1000 and stop after ten, `blockHash` null. `/block/height/{h}` lists orphans too, so the main-chain entry is taken and `txCount` counts its `tx` list. No fee endpoint, so gas stays unsupported. OP_RETURN outputs have a null address and never become the recipient; their pushes go to `opReturn` from `pkscript`
- eCash Explorer serves eCash keyless through the Bitcoin ABC explorer at explorer.e.cash, which reads Chronik; `baseUrl` is the explorer root. Its JSON covers `/api/address/{address}/transactions` and `/api/blocks/{from}/{to}` only: the balance, single transactions and unspent outputs exist as HTML pages, so `balances` stays false, `getBalance` throws `UnsupportedOperationError` and automatic selection sends eCash balances to Blockchair. The explorer parses lowercase CashAddr with the `ecash:` prefix and answers anything else with a 500 page, so the provider checks the address through `@agntn/chains` and respells it first. A history row carries the net change of the address (`stats.deltaSats`) and never the other side: a negative change is a send from the address with `to: null` and `value` the change minus the fee (inputs minus outputs, absent on a coinbase), anything else a receive with `from: ""`. History is newest first with mempool rows on top (`pending` at block 0), `page` from 1 goes out as Chronik's `page` from 0 and `limit` as `take`, up to 100 (the explorer allows 200 and answers 500 above it); `sort: "asc"`, `startBlock` and `endBlock` throw. `timestamp` is when Chronik first saw the transaction, the block time only for one it never saw in its mempool. Token details stay in `raw` and `tokenTransfers` stays empty. `getBlockInfo` reads the range from the height below, newest first, to take the parent hash in one request; genesis gets the all-zero parent, a height past the tip an empty list and `NotFoundError`, `miner` stays empty and gas fields `"0"`
- XRPSCAN serves the XRP Ledger keyless at api.xrpscan.com, 10,000 requests a day; `baseUrl` is the `/api/v1` root. Amounts are drops (6 decimals). XRPSCAN wraps every amount as `{ value, currency }`: XRP as a JSON number of drops, which the HTTP client keeps as a string past 2^53 (spam payments ask for 10^17), issued currencies as decimal text in history and as a JSON number on `/tx/{hash}`, so the 16th digit there is whatever XRPSCAN's own float kept. An account the ledger never funded answers 200 with `error.error: "actNotFound"` on `/account/{address}` and 404 on its history; both read as `NotFoundError`. Only a Payment carries `value`, taken from `meta.delivered_amount` so a partial payment counts what arrived, with `Amount` as the fallback when that field is missing or `unavailable`, except on a payment flagged `tfPartialPayment`, which then reads `"0"` because its `Amount` was only a ceiling; issued values with an exponent outside the ledger's -96 to 80 are dropped; issued currencies go to `tokenTransfers` as `CURRENCY.ISSUER` with the decimals their own spelling needs, and a 40-hex code shows as its ASCII when printable. Any other transaction type keeps value `"0"` and `to` from `Destination` or `null`. A result other than `tesSUCCESS` reads as `failed`, `validated: false` as `pending`. History ignores `limit` and `forward`, returns 25 rows a page behind `marker`, newest first; the provider walks at most ten markers, so `limit` goes up to 100 with `page * limit <= 250`, and `sort: "asc"` or block bounds throw. Holdings come from `/account/{address}/assets`, positive trust line balances only. A ledger past the tip is a 500 from XRPSCAN, so it surfaces as `HTTPError`, not `NotFoundError`. No fee endpoint and no token filter on history, so gas and token transfers stay unsupported. Ledgers keep `miner` empty and gas fields `"0"`
- Nuthatch is the Etherscan-shaped `/api` of an indexer the user runs, so it has no default endpoint: `baseUrl` or `NUTHATCH_URL` names the nest root, and the constructor throws without one. `EXPLICIT_ONLY` in `core/resolve.ts` keeps it out of automatic selection and refusal hints, even on a chain where every other provider is plan limited; only `-p nuthatch` or `provider: "nuthatch"` reaches it. It reuses the Etherscan mappers and sends block bounds only when the caller sets them, since the nest refuses a range past its head. A `NUTHATCH_UNSUPPORTED:` result naming the `chainid` is `UnsupportedChainError`, any other `UnsupportedOperationError` with the nest's reason, and `NUTHATCH_INCOMPLETE:` a plain `ExplorerError`, never an empty list. Contracts, holdings and gas stay unsupported

## Architecture

Three-layer design: **CLI** → **Core** → **Providers**.

```mermaid
graph TB
  CLI["CLI (runCli)"] --> Core
  Core --> Providers
  Providers --> External["External APIs"]
  PiExt["Pi Extension"] -.-> Core
  PiExt -.-> Providers
  Types["types.ts"] -.-> Chains["@agntn/chains (runtime dep)"]
```

### Layer breakdown

- **Tool layer** (`tools.ts`, `tool-operations.ts`, `tool-lines.ts`): one definition per tool for MCP, Pi, OMP and the CLI (`runCli` with `default: "providers"` and `fallback: "balance"`); the executors load on the first call.
- **Core Layer** (`core/*.ts`): Domain types, provider registry (built lazily from the barrel list), HTTP client (native `fetch`, 15s timeout), ENS resolution (public APIs), input classification, error hierarchy.
- **Provider Layer** (`providers/*.ts`): 22 providers. Each file defines API types, helper mappers and a concrete `Provider` subclass with a static registry key, exports that class, and ships as its own bundle so `create()` can import it alone.
- **Pi Extension** (`extensions/pi/explorers.ts`): registers `explorersTools()` through `registerPiTools`, with `renderResult` drawing `terminalLines()`. Loads live `src/tools.ts` from a checkout and the relative `dist/tools.mjs` from an installed package, without self-importing the package by name. `extensions/omp/explorers.ts` registers the same list through `registerOmpTools` for OMP.

### Provider categories

1. **Multi-chain EVM** (etherscan, blockscout): support 10 EVM chains each
2. **Bitcoin/Ethereum bridge** (blockchair): dashboard API for Bitcoin, Bitcoin Cash, Litecoin, Dogecoin, Ethereum, eCash and Zcash
3. **Esplora-compatible UTXO** (mempool, blockstream): Mempool serves Bitcoin, Litecoin and Pepecoin; Blockstream serves Bitcoin as an independent backend
4. **Bitcoin SV** (whatsonchain): WhatsOnChain REST, the only Bitcoin SV backend
5. **Bitcoin Gold** (blockbook): Blockbook REST at btgexplorer.com, the only Bitcoin Gold backend
6. **Bitcoin Cash** (haskoin): Haskoin Store REST at api.haskoin.com, the keyless Bitcoin Cash backend ahead of keyless Blockchair
7. **eCash** (ecash): explorer.e.cash JSON for history and blocks, ahead of keyless Blockchair for those reads
8. **Single-chain non-EVM** (solscan, helius, ton, tronscan, aptos, blockberry, koios, turbo, ario, arweave, dcrdata, horizon, xrpscan): capabilities mirror only their explorer APIs; Aptos is explicitly unsupported

## Patterns

- **Lazy registration**: `providers/index.ts` exports `builtins` with metadata and a `load` per provider, and `core/registry.ts` builds its map the first time anything asks the registry. `create(name)` awaits `load()` once and caches the class; every metadata question stays synchronous. `register(providerClass, meta)` covers provider classes living outside the package.
- **Nothing runs on import**: library modules evaluate to declarations only. Derived values wait for their first use, such as `entries()` in the registry, `decoder()` in mempool and `agent()` in the HTTP client. `dist/cli.mjs` is the one bundle that runs on load, because it starts the CLI, and `sideEffects` in `package.json` says so.
- **Measuring that claim**: after `pnpm build`, `node scripts/side-effects.ts` bundles a bare import of every entry from a copy of `dist/` outside the package, with each module treated as side-effectful, because rolldown obeys the `sideEffects` field over `moduleSideEffects` inside it, and prints what survives tree shaking, bare imports of external packages left out. Every entry except `dist/cli.mjs` prints 0 B.
- **String-only values**: All wei/satoshi/native amounts are strings (`Balance.balance`, `TokenBalance.balance`). The HTTP boundary preserves unsafe JSON integers as strings; `formatWei()` converts amounts for display.
- **Optional methods**: `getTxDetail`, `getUtxos`, `getPubkey`, `getContractInfo`, `getTokenBalances`, `getTokenTransfers`, `getGasData`, and `getBlockInfo` are optional on `Provider`. Take one through `requireOperation()` in `core/provider.ts`, which checks the `capabilities` flag and the method and returns it bound; the CLI, MCP, Pi, OMP and the docs worker all do.
- **Lazy executors**: `runCli` builds every command from its schema before it reads the line, so `tools.ts` imports nothing but `@agntn/tools` and `tool-limits.ts`; the core and the providers load inside `execute` through `loadOperations()`.
- **Chain normalization**: `normalizeChain()` delegates to `getChain()` from `@agntn/chains` and returns the canonical `ChainKey`. Aliases and display names both resolve (`ethereum→eth`, `btc→bitcoin`, `arb→arbitrum`). Missing input defaults to `eth`; unknown names and the empty string throw.
- **Chain from the address**: without an explicit chain, `withProvider()` takes the chain `inferChain()` reads off the address when `identify()` from `@agntn/chains` finds exactly one, or when a provider serves only one of the chains it finds. A legacy Bitcoin address fits Bitcoin SV too and reads as Bitcoin, the chain `FORK_OF` in `core/input.ts` names as the owner of that format, unless the explicit provider serves only Bitcoin SV; EVM addresses, ENS names and unknown formats keep the defaults. `resolveInput()` throws `AddressChainMismatchError` before any request only when the requested chain rejects the address and every chain that accepts it belongs to another family: shared formats such as Bitcoin P2SH on Litecoin and forms the validators miss, such as raw TON or hex TRON, still reach the provider
- **Provider auto-selection**: `resolveProvider()` checks env vars, chain support, and an optional requested capability without loading provider modules. `withProvider()` keeps explicit choices strict and retries automatic reads once on another available built-in after `RateLimitError`, `BlockedError`, `PlanRestrictedError`, a `TransportError` that is not the caller's abort, or a 5xx `HTTPError`; when that retry fails too, its error keeps the first one as `cause`. A `PlanRestrictedError` on an automatic read with a capability puts that provider last for the same chain and capability for an hour, keyed to its credentials, and out of the fallback slot; it still answers when nobody else serves the read. Keyless Blockchair ranks behind every provider that needs no key, so Bitcoin retries on Blockstream, while Litecoin, with no second keyless backend, retries on Blockchair. 429 waits on that backend happen in `Provider` first. The callback must be safe to run twice. A sixth `signal` argument reaches the created provider as `ProviderConfig.signal` and cancels its requests and 429 waits; once it aborts, the read never falls back. MCP passes the request's signal, Pi and OMP the one `execute` receives, and each also hands it to `resolveAddresses()` so ENS lookups stop with it
- **Error sanitization**: `HTTPError` strips API keys from URLs in error messages. `normalizeError()` wraps unknown errors into typed `ExplorerError` subclasses.
- **Terminal boundary**: the text on every surface is one line of JSON from `compactJson()`, where control bytes, C1, bidi marks and line separators arrive escaped, so a token symbol, contract name or decoded method cannot pose as the next result line. The Pi and OMP result renderers run each line of `terminalLines()` through `sanitizeLine`, and split an OP_RETURN message or an inscription body themselves to indent its continuation lines.
- **Payload boundary**: every surface answers with the normalized shape as unindented JSON, since indentation adds about a fifth to the tokens of the same record, and withholds the heavy optional fields until a call asks: `Transaction.raw` behind `raw: true` on `explorers_tx_history` and `explorers_tx_detail`, `ContractInfo.abi` and `sourceCode` behind `abi` and `sourceCode` on `explorers_contract`. `explorers_tokens` defaults `nonZeroOnly` to true and lists fifty holdings unless `limit` (up to 100) says otherwise, with `total` counting every holding, since a wallet that has been airdropped at holds thousands. `explorers_tx_history` and `explorers_token_transfers` list ten rows unless `limit` says otherwise. A `limit`, `page` or block bound of `0` reads as left out, because OMP fills an unused number with `0`. `getTokenBalances()` itself still returns every holding. `explorers_utxos` cuts unspent outputs at the same fifty with the same `total`, plus `confirmed` (base units) and `pending` over every output, because an address that collects dust answers with thousands of them (1.8 MB of JSON for the Bitcoin SV genesis address), and `getUtxos()` still returns every one. The library types keep every field.

## Anti-patterns to avoid

- Writing a provider file without adding its chains and capabilities to `builtins` — the class never reaches capability-aware routing, and `test/unit/registry.test.ts` fails
- A top-level call in a module the library entry can reach (`new Set()`, `Object.keys()`, a decoder, a prebuilt map) - it pins that module into every consumer bundle, which `node scripts/side-effects.ts` reports as bytes above 0
- Calling an optional provider method without `requireOperation()`, or pairing a capability flag with a method by hand, since unsupported operations stay absent at runtime
- Assuming EVM address formats work on non-EVM chains (Solana base58, TON base64, TRON base58/hex)
- Hardcoding chain names — always use `normalizeChain()` for user input

## Test coverage gaps

**Covered** (46 test files): provider base/registry, provider resolution, HTTP client, path safety, amount formatting, errors, input classification, chain normalization, CLI argument routing, extension integration, the built bin's `mcp` source switch and its start through the shebang, the commands `runCli` builds, the Pi and OMP result lines, `@agntn/explorers/mcp` imported by package name, the docs worker's rate limit key, every package `docs/` imports declared in its manifest, plus all twenty-two providers. `test/unit/docs-rate-limit.test.ts` loads `docs/server/utils/query.ts` through the `#shared` and `@agntn/explorers` aliases in `vite.config.ts`, with the real `ohash` from `docs/node_modules`, which the one workspace install fills in CI too. `test/unit/cli-bin.test.ts` runs `dist/cli.mjs`, so it needs `pnpm build` first, as CI does, and stops before any test when a source file, `package.json`, the lockfile or `build.config.ts` is newer than that bundle.
**CLI coverage**: help without backend imports, errors for unknown chains, provider listing, capability refusals with their provider hint, and mocked balance, transaction and token reads. Successful contract, transfer, gas, and block command execution remains untested.
**Test style**: Focused unit tests for local contracts and mocked explorer API responses. Live roundtrips belong in `test/live` and run only through `pnpm test:live`.

## Dependencies

- `@agntn/chains`: canonical chain registry. `ChainKey` for keys, `getChain()` for alias resolution, `create(key)` for per-chain metadata like symbol and chain ID. Stays external to the bundle, so a consumer and this library share one registry instead of two.
- `@agntn/tools`: one tool definition for MCP (`@modelcontextprotocol/server` 2.x), Pi, OMP and the CLI, with validation and sanitizing in its core
- `zod`: response schemas in several providers
- `obuild`: builds the bundle from `build.config.ts`, with one input per file in `src/providers/` read off the disk
- `vite-plus`: lint, format and tests from one `vite.config.ts`; `vp test` runs Vitest 5. Test files import from `vite-plus/test`

## Build & Scripts

```bash
pnpm build          # obuild → dist/
pnpm dev            # obuild --stub
pnpm typecheck      # build, then tsc --noEmit
pnpm lint           # vp lint, then vp fmt --check; CHANGELOG.md stays out of the formatter
pnpm test           # vp test watch (unit, offline)
pnpm test:run       # vp test run (unit, offline)
pnpm test:live      # public explorer roundtrips, not CI
pnpm release        # build, test, changelog, tag, push; CI publishes the tag
```

Every pull request and push to `main` runs lint, typecheck, build and `pnpm test:run` on Node 26 through `.github/workflows/test.yml`; `autofix.yml` commits what `pnpm fmt` changes back to the pull request branch.
